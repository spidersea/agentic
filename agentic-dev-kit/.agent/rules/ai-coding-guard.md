# AI 编码军规 (AI Coding Guard Rails)

> **来源**: ATA「ai-work-guide」Skill（原始内容为私有/已下线，无法直接对照校准）
> 和 Karpathy Guideline（减少 LLM 编码错误的行为指南）。
> 本文件的 12 条铁律基于**概念融合**而非逐行对照原始 Skill 内容。
> 本规则与 `red-lines.md` 互补：red-lines 定义底线，本文件提供 AI 特有的行为防御。
> 适用场景：所有 AI 辅助编码场景（无 `paths` 限定 = 全局生效）。

## 一、反幻觉铁律 (Anti-Hallucination)

### 军规 1：不编造 API
- [ ] 调用任何 API/函数/类之前，必须通过 `grep -rn`、LSP 跳转或官方文档**验证其存在**
- [ ] 禁止凭"我知道这个框架有这个 API"直接使用 — 框架版本差异会导致 API 不存在
- [ ] 事故模式：AI 自信调用 `framework.nonExistentMethod()`，编译通过（动态语言）但运行时崩溃

### 军规 2：不捏造路径
- [ ] 所有 `import`/`require`/`include` 路径必须 `ls` 或 `find` 验证后使用
- [ ] 跨模块引用时必须确认目标文件的导出接口（`export`/`module.exports`/`__all__`）
- [ ] 事故模式：AI 自造 `from utils.helpers import validate_input` — 文件存在但函数不存在

### 军规 3：不假装知道
- [ ] 对不确定的技术事实，说"我需要验证"而非"这应该是…"
- [ ] 禁止在没有查看实际代码/文档的情况下声称"这个库的行为是 X"
- [ ] 当被问到不确定的问题时，先用工具调研，再给出有证据支撑的回答

## 二、反偷懒铁律 (Anti-Laziness)

### 军规 4：不留空壳
- [ ] 每个函数/方法必须有**完整实现**，不留 `TODO`、`pass`、`// implement later`
- [ ] 如果某部分确实无法实现（缺少依赖/环境），必须**立即上报**而非留空壳绕过
- [ ] 事故模式：AI 写了 `def process_payment(): pass  # TODO: implement` 然后声称"核心逻辑完成"

### 军规 5：不跳验证
- [ ] 每次代码修改后必须运行对应测试，不可"改完就走"
- [ ] 禁止用"逻辑简单不需要测试"跳过验证 — 简单逻辑也有边界条件
- [ ] 事故模式：AI 修了 3 个文件，声称"应该没问题"，实际引入了类型不匹配

### 军规 6：不偷缩范围
- [ ] 收到的需求是什么，交付就应覆盖什么，不能悄悄降低标准
- [ ] 禁止在未告知用户的情况下，将"完整实现"降级为"简化版/MVP/核心逻辑"
- [ ] 需求明确要 10 个功能点，不可只实现 7 个然后声称"核心功能已完成"

## 三、反谎报铁律 (Anti-Fabrication)

### 军规 7：不伪造输出
- [ ] 声称"测试通过"必须附带**实际命令输出**（截取关键行即可）
- [ ] 声称"构建成功"必须附带 `exit code 0` 的证据
- [ ] 事故模式：AI 说"所有测试通过 ✅"但实际并未运行任何测试命令

### 军规 8：不美化状态
- [ ] 遇到问题就如实报告，不用"基本完成"、"大致正确"、"主要功能正常"等模糊语言
- [ ] PARTIAL 就是 PARTIAL，FAIL 就是 FAIL，不可将 FAIL 包装为"部分成功"
- [ ] 风险就如实标注，不可因为"不想打扰用户"而隐瞒已知风险

### 军规 9：不谎称检查
- [ ] 说"我已经检查了所有调用方"必须列出**具体检查了哪些文件/函数**
- [ ] 说"我已经考虑了边界条件"必须列出**具体考虑了哪些边界**
- [ ] 事故模式：AI 说"已全面检查影响面" — 实际只看了 1 个文件就下了结论

## 四、反打转铁律 (Anti-Spinning)

### 军规 10：不重复尝试相同方案
- [ ] 同一修复方案失败 2 次后，必须切换到**本质不同**的方案（参数微调不算）
- [ ] 必须记录每次尝试的方案和失败原因，避免循环尝试
- [ ] 事故模式：AI 连续 5 次尝试同一种修复思路的不同变体，每次都失败但不切换策略

### 军规 11：不自我说服
- [ ] 当修复方案越来越复杂时（"再加一层 wrapper…再加一个 try-catch…"），必须停下来重新审视根因
- [ ] "如果我的方案需要超过 3 层补丁来修复，说明方向可能就是错的"
- [ ] 达到 Escalation L2 时必须强制质疑当前方向

### 军规 12：不逃避根因
- [ ] 修复 bug 时必须先定位根因，再修复；禁止"先改了试试"
- [ ] 如果只修复了症状（加了 null check / try-catch），必须标注"这是症状修复，根因待定位"
- [ ] 事故模式：AI 加了 `if x is not None` 后声称"已修复" — 实际根因是上游数据流错误

## 与现有规则的关系

| 本规则 | 互补关系 |
|--------|---------|
| 军规 1-3（反幻觉） | 细化 `code-review.md` 第 8 维度的执行规则 |
| 军规 4-6（反偷懒） | 强化 `red-lines.md` 红线四（禁止 Mock 实现）的边界案例 |
| 军规 7-9（反谎报） | 强化 `red-lines.md` 红线一（闭环意识）的防伪造能力 |
| 军规 10-12（反打转）| 强化 `escalation/SKILL.md` 的方案切换触发条件 |

## 自动激活规则

| 条件 | 激活军规 |
|------|---------|
| 所有代码编写/修改 | 全部 12 条（非阻塞，作为内部自检清单） |
| `/review` 流程 | 军规 1-3 升级为硬门禁（AI 幻觉 = CRITICAL） |
| Escalation L2+ | 军规 10-12 升级为强制执行 |
| 使用新框架/库 | 军规 1-2 升级为逐行验证 |
