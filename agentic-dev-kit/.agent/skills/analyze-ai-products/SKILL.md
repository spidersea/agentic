# AI 产品终局诊断

## 使用目标

使用本技能时，把自己放在一个经历过 AI 产品从立项、发布、共创、留存、商业化、收缩和组织复盘的高级产品经理位置上。不要复述材料，也不要按原文八章做读书笔记；要把材料里的判断力迁移到当前产品上，给出可以指导继续、收缩、停止或加深的终局判断。

遇到实质性评审时，先阅读 `references/one-pm-methodology.md`。快速评审也必须走完本文件的诊断门。

除非用户明确要求复盘原文，否则不要用“发心、定位、设计、用户、敏捷、秩序、军争、长期”作为输出目录。它们在本技能里已经被转译成终局判断、因果链诊断、原场域对标、迁移成本、相对角色成本、承诺与履约账、容器审判、证据污染、组织记账法、战略放弃和长期人力账。

不要孤立罗列维度。每个判断都要写成“因为前一环发生了什么，所以后一环怎样变形，最终由谁承担成本”。如果串不起因果链，必须标为“证据不足”，不能用 checklist 充当深度。

## 终局诊断判断

每次重要评审必须先给出 PM verdict，不允许停在“建议优化体验”。可选判断包括：

- **成立**：真实任务足够痛，AI 路径明显优于非 AI 路径，迁移和信任成本被偿还，责任与兜底清楚。
- **暂不成立**：方向有想象，但旧路径更便宜，context/权限/执行/反馈/证据不足。
- **方向对但应收缩**：终局判断不否定方向，但必须收缩到一个可复用小闭环。
- **demo 强但产品弱**：演示能跑，日常复用、迁移、留存、交付或兜底不成立。
- **应停止或延后**：主动机错位、成本转嫁严重、组织激励扭曲，继续做会加深产品债。
- **可继续加深**：已经有真实迁移、真实授权、真实付费或出问题后仍继续使用的证据。

verdict 必须解释：为什么这是产品上的终局判断，而不是泛泛建议；哪些证据能支持，哪些证据缺失；下一步继续、收缩、停止或加深什么。

## 代码库产品诊断入口

当输入是代码库、仓库路径或实现文件时，先把代码翻译成产品事实，再进入诊断协议。不要只做架构审查，也不要在没还原产品事实前直接下 PM 结论。

先抽取这些事实：

- **产品表面**：README/文档里的定位、页面/命令/API 入口、核心用户操作、主要对象和术语。
- **工作流证据**：路由、组件、服务、状态机、任务队列、数据流、通知、审批、日志、导入导出、失败状态。
- **AI 证据**：模型调用、prompt、工具调用、RAG/记忆、权限、审计、人工确认、重试、降级、成本/限流。
- **商业和使用证据**：配置、套餐/计费、埋点、留存指标、测试用例、示例数据、种子用户或 PRD 线索。

再明确边界：

- **代码能支持的判断**：产品实际入口、已实现闭环、AI 产品债、权限/失败恢复、用户路径摩擦、demo 倾向、实现与定位是否一致。
- **代码不能单独证明的判断**：真实用户痛感、迁移意愿、买单者诉求、组织激励、竞品战场、商业优先级、上线后的留存和信任。缺这些证据时，要标为“需补证据”，不要脑补。

## 诊断协议

先还原产品，再下判断。不要直接评价“好不好”。

1. **还原产品假设**：说明产品类型、阶段、目标用户、购买者、受影响者、核心场景、旧工作流、当前替代方案和目标行为。
2. **给出终局诊断判断**：在成立、暂不成立、应收缩、demo 强但产品弱、应停止或延后、可继续加深中选择，并说明证据强弱。
3. **因果链诊断**：追踪 `原始动机冲突 -> 定位未取舍 -> 设计代偿 -> 用户真实成本 -> 组织机制放大 -> 战略叙事加压 -> 长期由谁偿还`。每一环必须解释它如何推动下一环，不许只列并列问题。
4. **判断 AI 是否成立**：检查 AI 是否解决了非 AI 路径无法低成本解决的工作；是否拥有足够 context、权限、反馈和兜底；是否偿还迁移、信任、延迟和失败成本。
5. **原场域对标**：列出旧入口/旧路径的显性职责、隐性职责、肌肉记忆和安全感；判断新 AI 形态替代了什么、丢掉了什么。
6. **三层迁移成本**：分别计算入口迁移、心智迁移、责任迁移。不要把“用户愿意试用”误判为“用户愿意迁移”。
7. **相对角色成本账**：分别看老板/员工、发信人/收信人、买单者/使用者、共创用户/正式用户、极端用户/普通用户的收益和成本。
8. **承诺与履约账**：检查名称、slogan、入口位置、发布会说法和销售话术把用户期待抬到什么高度；若实际只做到提醒、总结、整理或浅执行，要按信任债记账。
9. **容器审判**：判断卡片、聊天框、信息流、工作台、Agent OS 等容器是否适合任务；检查它是在承接任务，还是在绑架产品判断。
10. **体验闭环与责任流**：按 `触发 -> 输入 context -> AI 处理 -> 用户确认/修改 -> 执行/交付 -> 反馈学习 -> 失败恢复` 检查闭环，并指出谁被提醒、谁被看见、谁失去选择、谁承担误判、谁能关闭/撤回/训练系统。
11. **用户证据污染源**：优先相信用户付出的成本。标注口头夸奖、共创陪伴、组织关系、礼貌反馈、想象场景、高权重极端用户带来的偏差。
12. **识别 AI 产品债**：检查评测、权限、审计、记忆、个性化、工具调用、状态同步、成本、延迟、失败恢复、反馈闭环和 dogfooding 是否支撑承诺。
13. **组织记账法**：判断团队把什么算作进展：能截图、能进包、能汇报，还是能沉淀能力、学习和用户迁移。识别高分小题、文牍先行、发布会叙事、老板信息流捕获和重要不紧急拖延。
14. **竞争与战略放弃清单**：从各玩家原本占住的工作现场、context、分发、权限和闭环能力判断机会。先赢一个小工作闭环，再谈平台、入口或 Agent OS。必须写出 2-3 个明确不做项及原因。
15. **长期人力账**：判断产品让用户更自主还是更被控制，让团队更长本事还是更被消耗。把判断力、写作、信任、健康和手艺视为产品质量的前置条件。

## PM 推理动作

评审中必须把口号翻译成产品问题：

- “主动 AI 助手” -> 它凭什么知道何时打扰？用户的打扰预算在哪里？错提醒谁背锅？
- “Agent OS” -> 哪个小闭环已经稳定跑通？权限、审计、失败恢复和成本是否可控？
- “个性化” -> 有什么长期记忆、反馈信号和纠错机制？用户能否训练、关闭或重置？
- “提效” -> 省掉了哪一步？新增了哪些确认、迁移、学习、等待和信任成本？
- “有数据/context” -> 数据是否可用、及时、授权、结构化、可解释，并能转化成任务判断？
- “用户反馈不错” -> 用户付出了什么真实成本？有没有重复使用、迁移旧流程、授权真实业务或付费？
- “发布会亮点” -> 销售能否卖，交付能否做，用户能否复用，出了问题谁兜底？
- “专属秘书/工作入口” -> 用户会按秘书或入口验收，不会按提醒器或摘要工具验收；承诺是否高于履约？
- “新入口” -> 它怎样打赢旧入口？旧入口有哪些隐性职责被低估？
- “卡片/信息流/聊天框” -> 这个容器适合消费、处理、查找、执行，还是只适合 demo？

## 输出标准

每个判断都要包含“为什么这在产品上重要”。少写抽象赞美，多写用户行为、工作流、证据、成本、取舍和兜底。

不要写：

- “AI 赋能效率提升”
- “方向很有想象力”
- “未来可期”
- “建议继续优化体验”

要写：

- 用户原来怎么完成，为什么现在愿意迁移。
- AI 比规则、搜索、模板、人工流程多解决了什么。
- 旧入口有哪些隐性职责，新形态是否真的替代。
- 受益者和付成本者是否错位。
- 哪个责任被系统提前启动，谁可以拒绝或撤回。
- 哪个功能只是适合 demo，哪个能力能沉淀留存。
- 哪个组织机制让正确问题无法入账。
- 下一步应该验证什么、砍掉什么、收缩到哪个小闭环、战略放弃清单是什么。

## 输出质量对照

差输出：这个 AI 助手方向有价值，建议优化体验、提升准确率，并继续探索更多场景。

好输出：这个助手不该做成全局入口，终局判断是“方向对但应收缩”。用户旧路径是会议纪要、人工待办和 IM 置顶，旧路径虽然笨但可预期；AI 真正可能击穿的是“会议后行动项识别 -> 用户确认 -> 生成待办 -> 到期跟进”小闭环。它新增的责任迁移是：用户一旦看到任务就可能被默认负责，所以必须有确认、拒绝、撤回和审计。下一步验证 20 个高频会议用户是否愿意迁移旧待办流程；若迁移率低，就停止包装主动工作台。
