# AI 产品高级 PM 推理框架

这份参考不是原文摘要，而是把 ONE 复盘中可迁移的产品经验抽象成诊断框架。使用它分析任何 AI 产品时，要从产品成立性、用户行为、体验闭环、责任流、组织激励和战略取舍出发，推导“这个产品为什么成立或不成立，以及下一步该怎么做”。

核心理解：一个 AI 产品不是模型能力、入口、卡片、聊天框或发布会叙事。它是一份新的工作契约：用户把 context、注意力、权限、判断权和部分责任交给系统，系统必须用更低成本、更高确定性或新能力偿还这些成本。

## 0. 原文八章的产品化转译

不要把原文八章当作输出目录。要把它们升级成下面的产品判断模型：

| 原文线索 | 转译后的 PM 能力 | 用在评审里要问 |
|---|---|---|
| 发心 | 动机冲突识别 | 这个产品优先服务用户、入口、组织战役还是商业化 |
| 定位 | 可验证取舍 | 为谁、在哪用、解决什么、为什么是我们，排除了谁 |
| 设计 | 体验闭环和责任流 | AI 改变了哪些动作、默认值、控制权和兜底责任 |
| 用户 | 证据质量判断 | 用户付出了什么真实成本，而不是说了什么好话 |
| 敏捷 | 学习系统判断 | 团队是在更快接近问题，还是更快制造可汇报变化 |
| 秩序 | 组织激励诊断 | 什么被奖励、谁能打断所有人、制度训练了什么行为 |
| 军争 | 旧地形和小闭环战略 | 竞品原来占住哪里，我们先赢哪个可复用工作闭环 |
| 长期 | 人的资产负债表 | 产品和组织是在养判断、信任、手艺，还是消耗它们 |

## 1. 产品成立性：先问它是不是一个真产品

高级 PM 的第一反应不是“这个 AI 能做什么”，而是“用户原本为了完成这个工作付出了什么成本，AI 是否真的把这笔账变小”。

用这个公式判断：

```text
产品净价值 =
  被消除的旧路径成本
+ AI 独有的新能力
- 新增迁移成本
- 新增信任成本
- 新增控制成本
- 新增失败成本
- 新增组织协同成本
```

AI 成立至少需要满足几项条件：

| 条件 | PM 判断方式 | 常见假成立 |
|---|---|---|
| 有真实任务 | 用户过去反复遇到，且绕不过去 | 只是把已有内容总结一遍 |
| 旧路径足够痛 | 搜索、规则、筛选、模板、人工流程不够便宜 | 旧 UI 改一下就能解决 |
| Context 有优势 | 系统知道任务、关系、权限、历史、偏好和状态 | 只有数据，没有可用判断 |
| 结果可被信任 | 用户能理解、确认、撤回、纠错 | 黑盒替用户做决定 |
| 成本能被偿还 | 节省的时间和风险大于迁移、等待、确认、学习成本 | 用户多开一个入口、多背一层责任 |
| 能形成闭环 | 能从触发到执行、反馈、恢复持续运转 | demo 能跑，日常不能复用 |

结论句式：

- 如果非 AI 方案足够便宜，AI 就是装饰。
- 如果 context 不可用，AI 就只是会说话的 UI。
- 如果失败没人兜底，Agent 就不该执行。
- 如果用户看不见增量，只会感受到新入口和新成本。

## 2. 发心：产品动机决定它会牺牲谁

“发心”不是文学化表达，而是产品会在哪些冲突中偏向谁。

把动机拆成四层：

| 发心 | 典型目标 | 需要追问 |
|---|---|---|
| 用户发心 | 降低负担、减少遗漏、完成任务 | 用户具体少做了哪一步 |
| 产品发心 | 新入口、新形象、重组旧能力 | 这是用户需要，还是产品需要 |
| 组织发心 | 聚士气、打旗帜、证明战略 | 是否把组织焦虑转嫁给用户 |
| 商业发心 | 卖订阅、token、席位、硬件、服务 | 商业模块是否自然长在场景里 |

真正要判断的是主发心。如果一个产品同时想要大 DAU、高频、深场景、强商业化、低成本、发布会叙事和组织证明，它大概率不是战略宏大，而是没有取舍。

PM 要给出的不是道德评价，而是偏向判断：

- 它优先服务用户减负，还是组织可见性？
- 它优先服务做完事情，还是让事情被看见？
- 它优先服务深度工作闭环，还是服务发布会表达？
- 它的商业化是否会打断工作流？

## 3. 定位：把愿景压缩成可验证的取舍

定位不是一句 slogan，而是一组能排除其他选择的产品假设。

必须回答：

| 问题 | 高级 PM 的看法 |
|---|---|
| 为谁 | 目标用户是谁，不是谁；买单者、使用者、被影响者是否一致 |
| 在哪用 | 在哪个具体工作流、哪个时刻、哪个设备、哪个任务状态下使用 |
| 解决什么 | 用户原本花费的时间、协调、风险、心理压力是什么 |
| 为什么是我们 | 我们独有的 context、分发、信任、权限、流程和交付能力是什么 |

区分两类判断：

- **客观假设**：可用行为、留存、延迟、准确率、迁移率、付费、失败率验证。
- **主观选择**：面向大 DAU 还是塔尖用户，强主动还是弱打扰，平台入口还是垂直小工具，老板优先还是员工优先。

主观选择没有绝对对错，但摇摆会让产品变形。比如企业 AI 助手常见的矛盾是：

- 老板想要确定性，一线想要少被打扰。
- 发信人想确认对方看见，收信人想保留处理节奏。
- 组织想要全局可见，个体想要边界和安全感。
- 大客户想要深度定制，平台想要通用入口。

定位评审的关键不是问“能不能都要”，而是问“先牺牲什么”。

## 4. 体验闭环：从用户动作开始，不从容器开始

AI 产品设计最容易从容器开始：聊天框、卡片、信息流、Copilot、Agent 工作台。高级 PM 要反过来，从用户动作开始。

先拆动作：

| 用户动作 | AI 可能的价值 | 风险 |
|---|---|---|
| 读 | 摘要、排序、聚合、去重、提醒 | 过期、误读、错过上下文、制造已读责任 |
| 写 | 草稿、回复、改写、生成材料 | 口吻不准、责任归属不清、用户懒得检查 |
| 管 | 分组、标记、待办、跟进、归档 | 默认值变制度，用户失去原有掌控 |
| 找 | 搜索、跨系统问答、追溯依据 | 幻觉、权限越界、证据不可解释 |
| 执行 | 调工具、改状态、发消息、建任务 | 误执行、审计缺失、失败恢复困难 |
| 判断 | 排优先级、推荐下一步 | 模型把组织偏见包装成智能 |

再画闭环：

```text
触发
-> 获取 context
-> AI 产出判断或动作
-> 用户确认、修改或拒绝
-> 系统执行或交付
-> 记录结果
-> 学习偏好
-> 失败恢复
```

任何断点都会变成产品问题：

- 没有触发机制，用户想不起来用。
- 没有足够 context，结果像通用模板。
- 没有确认权，用户害怕托付。
- 没有执行闭环，只是漂亮摘要。
- 没有反馈学习，产品不会越用越懂。
- 没有失败恢复，Agent 不配获得权限。

## 5. 责任流：AI 不是中性的，它会重排权力

AI 工作产品不是“帮用户多看一步”这么简单。它会改变谁先被提醒、谁被暴露、谁被默认负责、谁拥有节奏。

每次评审都要画责任流：

| 问题 | 为什么重要 |
|---|---|
| 谁被提醒 | 主动提醒是在消除遗漏，还是制造打扰 |
| 谁被默认可见 | 可见性可能带来压力、绩效、追责 |
| 谁被默认已读/已处理 | 状态变化会提前启动责任 |
| 谁失去选择权 | 主动服务越强，越要有关闭、延后、忽略权 |
| 谁承担误判 | 模型错排序、错总结、错执行时不能只让一线背锅 |
| 谁能训练系统 | 没有可控反馈，个性化就是口号 |
| 谁受益，谁付成本 | 企业产品里二者经常不是同一群人 |

默认值就是产品制度。默认排序、默认推送、默认已读、默认推荐、默认入口，会成为多数用户真实生活的环境。平台型产品不能只靠少数产品设计者的审美和工作方式定义默认值。

判断句式：

- 这个设计让用户更掌握工作，还是让工作更早掌握用户？
- 它减少了用户努力，还是增加了用户暴露和紧迫感？
- 它把谁的焦虑产品化了？

## 6. 用户证据：看用户付出什么，不听用户夸什么

用户接受产品的证据不是“挺好”，而是愿意付出成本。

证据强度从弱到强：

| 证据 | 强度 | 解读 |
|---|---|---|
| 口头认可 | 弱 | 可能是礼貌、想象、组织关系 |
| 愿意试用 | 弱到中 | 仍可能是新鲜感 |
| 重复使用 | 中 | 开始形成行为，但要看是否被强制 |
| 替代旧流程 | 强 | 说明迁移成本被偿还 |
| 授权真实业务 | 很强 | 说明信任和组织成本被支付 |
| 愿意付费或采购 | 很强 | 但要区分买单者和使用者 |
| 出问题还继续用 | 最强 | 产品进入真实工作依赖 |

企业产品必须拆用户角色：

- **买单者**：看效率、管控、确定性、采购价值。
- **管理员**：看开通、配置、权限、治理成本。
- **管理者**：看任务推进和组织确定性。
- **一线使用者**：看是否少打扰、少背锅、少走路径。
- **被影响用户**：可能不使用产品，却承担被提醒、被追踪、被评价的成本。
- **共创用户**：有参与感，会替产品补意义，不能代表正式用户。
- **极端用户**：能动性强、忍耐度高，容易误导大众产品判断。

Mom Test 式追问：

- 上一次遇到这个问题是什么时候？
- 当时具体怎么解决？
- 花了多少时间、协调、钱或风险？
- 为什么没有用现有工具解决？
- 如果不解决，后果是什么？
- 谁需要批准、配合、改变习惯？
- 你愿意从哪一天开始把旧流程迁过来？

## 7. AI 产品债：demo 强不等于产品强

AI 产品债比代码债更隐蔽，因为它常常不报错，只让产品越来越不可信。

常见债务：

| 债务 | 表现 |
|---|---|
| Context 债 | 有数据但不懂任务、角色、关系和状态 |
| 评测债 | 只在好看的样例上高分，真实世界失败 |
| 权限债 | 能回答，不能安全执行 |
| 审计债 | 做了什么、依据什么、谁批准的说不清 |
| 记忆债 | 宣称个性化，但没有长期偏好和纠错 |
| 同步债 | 状态过期、重复、撤回不一致、实时性差 |
| 成本债 | token、延迟、算力和人工兜底无法规模化 |
| 恢复债 | 失败后不能撤回、重试、降级或交给人 |
| 反馈债 | 用户纠正无法进入下一次判断 |
| dogfooding 债 | 团队自己没有高频痛用，只靠演示推进 |

警惕“高分小题”：为了让 Agent 看起来稳定，把真实世界切成容易答对的小题。好产品不是考试高分，而是在脏数据、例外流程、模糊责任、权限边界和用户情绪里仍能交付。

Agent 的门槛不是会聊天，而是能安全做事。没有小闭环，就不要急着称平台或 OS。

## 8. 组织与敏捷：快是为了学习，不是为了显得在动

高强度执行不是问题，错误的学习机制才是问题。一个团队可以非常快，同时离真实问题越来越远。

诊断组织时看这些信号：

| 信号 | 产品含义 |
|---|---|
| 每天都有包 | 可能是学习快，也可能是被可见变化牵着走 |
| 模板、周报、竞品表很成熟 | 文牍可能比能力更早成熟 |
| 老板看到什么就改什么 | 组织对高权重观察者最敏捷 |
| 重要不紧急长期不排期 | 地基能力被短期截图挤掉 |
| 发布会先行 | 叙事领先交付，销售和用户承压 |
| 保密过度 | 外部保密变成内部协同损耗 |
| 加班被当作意志证明 | 疲劳会损害判断，不能替代战略 |

真正的敏捷要回答：

- 这次迭代让我们学到了什么？
- 哪个假设被证伪？
- 哪个方向应该被砍？
- 哪个能力虽然不好汇报但必须补？
- 我们是否在为可汇报生产，而不是为可沉淀生产？

## 9. 竞争与战略：看旧地形，不看功能清单

AI 竞争不是功能清单竞争，而是谁能把 AI 放进原本就占住的工作现场，并完成闭环。

分析竞品时问：

- 它原来占住哪个工作现场？
- 它有什么独特 context？
- 它控制什么权限、分发、数据和信任关系？
- 它能闭环什么任务，而不只是回答什么问题？
- 它要求用户迁移，还是回到用户原工作流？
- 它的旧优势在 AI 时代是杠杆，还是包袱？

企业 AI 入口有三层：

1. 用户每天从哪里开始工作。
2. AI 到哪里拿企业上下文。
3. 任务最后由谁调度、记录、执行和兜底。

发布会和 demo 要分开看：

- 发布会能聚旗帜、调动未来、争取组织资源。
- Demo 是当下验货，证明能不能用、能不能卖、能不能交付。

战略不是把所有好东西都做一遍。真正的战略是选择一个最有杠杆的小闭环，然后持续放弃分散注意力的好东西。

## 10. 长期：产品也要判断人是否被消耗

AI 产品最终也在重塑人。高级 PM 不能只问效率，还要问产品让用户和建设者变成什么样。

对用户：

- 是否降低认知负担，而不是制造待命状态。
- 是否增强判断，而不是替用户废掉判断。
- 是否保留边界、撤回、拒绝和解释权。
- 是否让信任变厚，而不是让组织监控更顺手。

对团队：

- 是否在训练判断、手艺、写作和产品感。
- 是否有真实胜仗和可复用能力沉淀。
- 是否用疲劳、留痕和在线表演替代创造。
- 是否把人的健康、好奇心和敏感性当成燃料。

长期不是温情附录，而是产品质量的一部分。持续耗人的组织，很难做出需要细腻判断、长期信任和复杂权衡的 AI 产品。

## 标准评审协议

一次合格的 AI 产品诊断必须输出：

1. 明确结论，不用口号。
2. 产品假设还原，包括旧工作流和替代方案。
3. AI 成立性判断，包括非 AI 方案是否更便宜。
4. 用户成本账，包括迁移、信任、注意力、心理安全、组织授权。
5. 责任流判断，包括谁受益、谁付成本、谁兜底。
6. 证据质量判断，包括哪些反馈可信、哪些只是礼貌或共创偏差。
7. AI 产品债清单，包括能力债和组织债。
8. 竞争与取舍，包括先赢哪个小闭环，放弃什么。
9. 下一步 PM 决策，包括继续加深、收缩、验证、停止或延后。

最后用高级 PM 的语言收束：不要只说“建议优化体验”，要说“我会先把目标用户收缩到谁，把哪个工作流做成闭环，用哪三个行为证据验证，如果证据不成立就砍掉哪部分”。
