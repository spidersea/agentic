# AI 产品终局诊断推理算子库

这份参考不是原文摘要，也不是章节翻译。它把《置身钉内》中可迁移的产品经验抽象成终局诊断推理算子。使用它分析 AI 产品时，不要只列 checklist，要追踪一个产品为什么成立、不成立、应收缩、应停止或可继续加深。

核心理解：一个 AI 产品不是模型能力、入口、卡片、聊天框或发布会叙事。它是一份新的工作契约：用户把 context、注意力、权限、判断权、节奏感和部分责任交给系统，系统必须用更低成本、更高确定性或新能力偿还这些成本。

## 0. 主链：从原始矛盾到长期偿还

原文真正可迁移的不是八个章节名，而是一条产品因果链：

```text
发心混杂
-> 定位不收束
-> 设计容器先行
-> 用户现场拆穿
-> 敏捷表层修补
-> 秩序固化偏差
-> 军争放大战线
-> 长期由人偿还
```

用在评审里时，不要只问“这个维度有什么问题”，而要问“哪个早期矛盾正在通过后续环节变成用户成本、组织债和长期损耗”。

前后逻辑是本方法的核心：发心不是单独的价值观，定位不是单独的口径，设计不是单独的交互，用户反馈不是单独的满意度。每一环都要解释上一环的矛盾如何在下一环变形；无法解释传导关系时，应标注证据不足，而不是把八个维度排成清单。

| 原文线索 | 终局诊断算子 | 必须追问 |
|---|---|---|
| 发心 | 原始动机冲突 | 产品优先服务用户、入口、组织战役、商业化还是个人/团队证明 |
| 定位 | 取舍是否闭合 | 为谁、在哪用、解决什么、为什么是我们、先牺牲什么 |
| 设计 | 容器审判和责任流 | 容器是否适合任务，AI 改变了哪些默认值、控制权和兜底责任 |
| 用户 | 证据污染识别 | 用户付出什么真实成本，反馈是否被共创、礼貌、组织关系污染 |
| 敏捷 | 学习还是修补 | 团队是在接近根问题，还是在让错误设计没那么痛 |
| 秩序 | 组织记账法 | 什么算进展，什么不能入账，制度训练人把时间投向哪里 |
| 军争 | 旧地形与放弃 | 各玩家原来占住哪里，我们先赢哪个闭环，明确不做什么 |
| 长期 | 人力资产负债表 | 产品和组织是在养判断、信任、手艺，还是把人当燃料 |

## 1. 终局诊断判断

高级 PM 的输出不是“建议优化”，而是 verdict。

| verdict | 使用条件 | 典型下一步 |
|---|---|---|
| 成立 | 真实任务足够痛，AI 有非 AI 难以替代的新能力，迁移与信任成本被偿还 | 继续加深闭环和规模化 |
| 暂不成立 | 旧路径更便宜，context/权限/反馈/兜底不足 | 补证据或暂停投入 |
| 方向对但应收缩 | 愿景太大，但某个小工作闭环可能成立 | 收缩到一个可复用闭环 |
| demo 强但产品弱 | 演示好看，日常复用、留存、交付或兜底不足 | 停止包装，补地基 |
| 应停止或延后 | 主动机错位，成本严重转嫁，继续做会加深产品债 | 停止、延后或换题 |
| 可继续加深 | 有真实迁移、授权、付费或出错后仍继续用的证据 | 加深个性化、治理、商业化 |

终局判断必须说明：它为什么不是审美判断，而是由任务、旧路径、迁移成本、责任流、证据质量和组织能力共同推出的产品结论。

## 2. 发心算子：动机不是道德，是未来会牺牲谁

把动机拆成四层：

| 发心 | 典型目标 | 诊断问题 |
|---|---|---|
| 用户发心 | 降低负担、减少遗漏、完成任务 | 用户具体少做了哪一步，少承担了什么风险 |
| 产品发心 | 新入口、新形象、重组旧能力 | 这是用户需要，还是产品需要 |
| 组织发心 | 聚士气、打旗帜、证明战略 | 是否把组织焦虑转嫁给用户 |
| 商业发心 | 卖订阅、token、席位、硬件、服务 | 商业模块是否自然长在场景里 |

判断主发心。一个产品若同时想要大 DAU、高频、深场景、强商业化、低成本、发布会叙事和组织证明，它不是宏大，而是没有取舍。

结论句式：

- 它优先服务用户减负，还是组织可见性。
- 它优先服务做完事情，还是让事情被看见。
- 它优先服务深度工作闭环，还是服务发布会表达。
- 它的商业化是否提前塞进了工作入口。

## 3. 定位算子：愿景必须压缩成先做什么

定位不是一句 slogan，而是一组能排除其他选择的产品假设。

必须回答：

| 问题 | 终局诊断标准 |
|---|---|
| 为谁 | 目标用户是谁，不是谁；买单者、使用者、被影响者是否一致 |
| 在哪用 | 在哪个工作流、哪个时刻、哪个设备、哪个任务状态下使用 |
| 解决什么 | 用户原本花费的时间、协调、风险、心理压力是什么 |
| 为什么是我们 | 独有 context、分发、信任、权限、流程和交付能力是什么 |
| 先牺牲什么 | 不服务谁、不做什么、不追哪些指标 |

区分两类判断：

- **客观假设**：可用行为、留存、延迟、准确率、迁移率、付费、失败率验证。
- **主观选择**：大 DAU 还是塔尖用户，强主动还是弱打扰，平台入口还是垂直小工具，老板优先还是员工优先。

主观选择没有绝对对错，但摇摆会让产品变形。

## 4. AI 成立算子：数据只是资格，不是胜势

AI 成立至少满足这些条件：

| 条件 | PM 判断方式 | 常见假成立 |
|---|---|---|
| 有真实任务 | 用户过去反复遇到且绕不过去 | 只是把已有内容总结一遍 |
| 旧路径足够痛 | 搜索、规则、筛选、模板、人工流程不够便宜 | 旧 UI 改一下就能解决 |
| Context 有优势 | 系统知道任务、关系、权限、历史、偏好和状态 | 只有数据，没有可用判断 |
| 结果可被信任 | 用户能理解、确认、撤回、纠错 | 黑盒替用户做决定 |
| 成本能被偿还 | 节省的时间和风险大于迁移、等待、确认、学习成本 | 用户多开一个入口、多背一层责任 |
| 能形成闭环 | 能从触发到执行、反馈、恢复持续运转 | demo 能跑，日常不能复用 |

判断句式：

- 如果非 AI 方案足够便宜，AI 就是装饰。
- 如果 context 不可用，AI 就只是会说话的 UI。
- 如果失败没人兜底，Agent 就不该执行。
- 如果用户看不见增量，只会感受到新入口和新成本。

## 4.5 承诺与履约账算子：说自己是什么，就按什么被验收

AI 产品的名字、入口位置、发布会口径和销售话术不是包装，它们会改变用户的验收标准。

| 承诺方式 | 用户会怎样验收 | 风险 |
|---|---|---|
| 提醒器 | 是否准时提醒、少漏事 | 可接受简单、边界清楚 |
| 摘要工具 | 是否省阅读时间、是否可追溯 | 错摘要和漏重点会伤信任 |
| 专属秘书 | 是否懂分寸、能推进、能兜底 | 只会整理就会被认为不履约 |
| 工作入口 | 是否比旧入口更省事、更可靠 | 新入口若只重排旧能力，会被旧路径打败 |
| Agent OS | 是否有稳定小 Agent、权限、审计、恢复和成本控制 | 没有小闭环就会变成宏大容器债 |

判断句式：

- 你说自己是秘书，用户就不会按提醒器宽容你。
- 你把入口放到首页，用户就会要求它打赢旧首页和旧工作路径。
- 发布会可以抬高预期，但抬高后的差额要用产品履约偿还。
- 承诺高于履约时，问题不是“体验需优化”，而是信任债开始累积。

## 5. 原场域对标算子：新入口先要打赢旧路径

AI 新入口最容易低估的竞争对手，是用户已经依赖的旧系统。

必须列出：

- **旧路径/旧入口**：用户现在从哪里开始工作。
- **显性职责**：旧路径明面上做什么，如展示、提醒、审批、搜索、记录。
- **隐性职责**：肌肉记忆、安全感、可预期、模糊查找、延迟处理、心理缓冲、责任边界。
- **新形态替代了什么**：它真实省掉了哪些动作。
- **新形态丢掉了什么**：它破坏了哪些旧路径优势。
- **迁移理由**：不依靠这个 AI，用户是否真的无法低成本完成任务。

旧系统常常不先进，但可预期。企业软件里，“够用”本身就是强惯性。

## 6. 三层迁移成本算子

不要把用户试用当作用户迁移。

| 迁移成本 | 诊断问题 |
|---|---|
| 入口迁移 | 用户原来从哪里开始，现在为什么要从新入口开始 |
| 心智迁移 | 旧系统按工具分工，新系统按事情/判断组织，用户是否信任这个判断 |
| 责任迁移 | 系统主动把事情端到眼前后，用户是否被提前启动责任 |

强主动产品尤其要回答：你凭什么现在推给我，我看见后是否马上背责。

## 7. 相对角色成本账算子

企业产品不是单一用户产品。每次诊断都要拆相对角色。

| 角色对 | 常见错配 |
|---|---|
| 老板 vs 员工 | 老板要确定性，员工要少被打扰和少背锅 |
| 发信人 vs 收信人 | 发信人要已读和推进，收信人要处理节奏和心理缓冲 |
| 买单者 vs 使用者 | 买单者看组织收益，使用者承担日常摩擦 |
| 管理员 vs 一线 | 管理员开权限，一线承受新流程 |
| 共创用户 vs 正式用户 | 共创用户体验产品+服务，正式用户只验收产品本身 |
| 极端用户 vs 普通用户 | 高能动/高权重用户不能代表沉默多数 |

收益和成本不在同一群人身上时，必须给出风险判断。

## 8. 容器审判算子：形式不能凌驾于内容

不要默认卡片、聊天框、信息流、Copilot、工作台、Agent OS 成立。先判断容器是否适合任务。

| 容器问题 | 诊断方式 |
|---|---|
| 适合什么动作 | 消费、阅读、处理、查找、执行、复盘、协同分别需要不同形态 |
| 丢掉什么能力 | 列表、分组、模糊查找、置顶、标未读、长文本空间、PC 操作可能被牺牲 |
| 是否只适合 demo | 展示强不等于日常工作强 |
| 是否反向塑造需求 | 容器先定后，团队是否在逼用户削足适履 |
| 是否产生容器债 | 为维持容器而不断打补丁，根问题没有被重问 |

判断句式：

- 卡片适合轻处理，不天然适合复杂工作。
- 聊天框适合表达意图，不天然适合状态管理。
- 信息流适合连续浏览，不天然适合责任确认。
- Agent OS 适合承载多个稳定 Agent，不适合替代小闭环验证。

## 9. 责任流算子：看见不是中性的

AI 工作产品会改变谁先被提醒、谁被暴露、谁被默认负责、谁拥有节奏。

必须问：

- 谁被提醒。
- 谁被默认可见。
- 谁被默认已读/已处理。
- 谁失去选择权。
- 谁承担误判。
- 谁能训练、关闭、延后、撤回系统。
- 谁受益，谁付成本。

默认值就是制度。默认排序、默认推送、默认已读、默认推荐、默认入口，会成为多数用户真实生活的环境。

## 10. 用户证据污染算子

用户接受产品的证据不是“挺好”，而是愿意付出成本。

证据强度从弱到强：

| 证据 | 强度 | 解读 |
|---|---|---|
| 口头认可 | 弱 | 可能是礼貌、想象、组织关系 |
| 愿意试用 | 弱到中 | 仍可能是新鲜感 |
| 重复使用 | 中 | 开始形成行为，但要看是否被强制 |
| 替代旧流程 | 强 | 说明迁移成本被偿还 |
| 授权真实业务 | 很强 | 说明信任和组织成本被支付 |
| 愿意付费或采购 | 很强 | 但要区分买单者和使用者 |
| 出问题还继续用 | 最强 | 产品进入真实工作依赖 |

污染源：

- 共创陪伴：用户理解了产品团队上下文，正式用户不会继承。
- 礼貌反馈：用户不想伤害你或合作关系。
- 组织关系：客户、供应商、平台方关系影响表达。
- 想象场景：用户理论上喜欢学习或效率，实际工作时不想被打断。
- 高权重极端用户：老板、KP、专家用户有真实痛点，但不可直接外推。
- 计划外用户奏效：非目标用户愿意用，可能说明真正机会不在原定位。

## 11. AI 产品债算子

AI 产品债比代码债更隐蔽，因为它常常不报错，只让产品越来越不可信。

| 债务 | 表现 |
|---|---|
| Context 债 | 有数据但不懂任务、角色、关系和状态 |
| 评测债 | 只在好看的样例上高分，真实世界失败 |
| 权限债 | 能回答，不能安全执行 |
| 审计债 | 做了什么、依据什么、谁批准的说不清 |
| 记忆债 | 宣称个性化，但没有长期偏好和纠错 |
| 同步债 | 状态过期、重复、撤回不一致、实时性差 |
| 成本债 | token、延迟、算力和人工兜底无法规模化 |
| 恢复债 | 失败后不能撤回、重试、降级或交给人 |
| 反馈债 | 用户纠正无法进入下一次判断 |
| dogfooding 债 | 团队自己没有高频痛用，只靠演示推进 |

警惕高分小题：为了让 Agent 看起来稳定，把真实世界切成容易答对的小题。好产品不是考试高分，而是在脏数据、例外流程、模糊责任、权限边界和用户情绪里仍能交付。

## 12. 组织记账法算子

一个团队可以非常快，同时离真实问题越来越远。

诊断组织时不要只问“快不快”，要问“什么算进展”。

| 被记账为进展 | 可能无法入账但更重要 |
|---|---|
| 能截图 | 偏好学习、关系理解 |
| 能进包 | 权限、审计、失败恢复 |
| 能写 changelog | 长期记忆、反馈闭环 |
| 能让老板今晚验收 | 自定义、关闭权、心理安全 |
| 能追平竞品清单 | 可复用小闭环 |

判断句式：

- 敏捷若服务于学习，会更快接近正确问题。
- 敏捷若服务于证明，会更快制造变化，也更难承认方向需要重来。
- 团队每天都在动，却没有更接近正确问题，不叫敏捷，叫奔波。

## 13. 竞争与战略放弃清单算子

AI 竞争不是功能清单竞争，而是谁能把 AI 放进原本占住的工作现场，并完成闭环。

分析竞品时问：

- 它原来占住哪个工作现场。
- 它有什么独特 context。
- 它控制什么权限、分发、数据和信任关系。
- 它能闭环什么任务，而不只是回答什么问题。
- 它要求用户迁移，还是回到用户原工作流。
- 它的旧优势在 AI 时代是杠杆，还是包袱。

企业 AI 入口有三层：

1. 用户每天从哪里开始工作。
2. AI 到哪里拿企业上下文。
3. 任务最后由谁调度、记录、执行和兜底。

战略不是把所有好东西都做一遍。真正的战略是选择一个最有杠杆的小闭环，并持续放弃分散注意力的好东西。

必须输出战略放弃清单，至少列出 2-3 个明确不做项及原因。没有“不做什么”的战略，不是战略，是愿望清单。

## 14. 发布会、Demo、销售、交付算子

发布会可以调动未来，但不能替代交付。

| 表达形态 | 能证明 | 不能证明 |
|---|---|---|
| 发布会 | 旗帜、资源、组织动员、外部叙事 | 用户迁移、销售可卖、交付可做 |
| Demo | 当下能跑、效果可见 | 日常留存、异常兜底、规模化成本 |
| 销售材料 | SKU、权益、价值表达 | 真实业务闭环 |
| 交付现场 | 能否落到客户流程 | 是否值得做成平台入口 |

终局叙事不能直接组织中局战斗。先赢消息、会议、待办、表格、知识问答等小仗，再谈平台、入口或 Agent OS。

## 15. 长期人力账算子

长期不是温情附录，而是产品质量的一部分。持续耗人的组织，很难做出需要细腻判断、长期信任和复杂权衡的 AI 产品。

对用户：

- 是否降低认知负担，而不是制造待命状态。
- 是否增强判断，而不是替用户废掉判断。
- 是否保留边界、撤回、拒绝和解释权。
- 是否让信任变厚，而不是让组织监控更顺手。

对团队：

- 是否在训练判断、手艺、写作和产品感。
- 是否有真实胜仗和可复用能力沉淀。
- 是否用疲劳、留痕和在线表演替代创造。
- 是否把人的健康、好奇心和敏感性当成燃料。

判断句式：

- 人不是项目资源，判断力不是无限透支账户。
- 如果团队只被燃烧，没有长出判断、技艺和可迁移经验，这段燃烧要重新估价。
- 快要分层：原型和低风险试错要快，用户心智、权限、责任、信任、地基能力不能乱快。

## 标准评审协议

一次合格的 AI 产品终局诊断必须输出：

1. 明确 verdict，不用口号。
2. 产品假设还原，包括旧工作流和替代方案。
3. 因果链诊断，追踪原始矛盾如何传导到后续产品问题。
4. AI 成立性判断，包括非 AI 方案是否更便宜。
5. 原场域对标，包括旧入口的显性和隐性职责。
6. 三层迁移成本，包括入口、心智、责任。
7. 相对角色成本账，包括谁受益、谁付成本、谁兜底。
8. 承诺与履约账，包括产品叙事抬高了什么期待，实际履约到哪一层。
9. 容器审判，包括形态是否适合任务。
10. 用户证据污染判断，包括哪些反馈可信、哪些只是礼貌或共创偏差。
11. AI 产品债清单，包括能力债和组织债。
12. 组织记账法，包括哪些重要能力不能入账。
13. 竞争与战略放弃清单，包括先赢哪个小闭环，明确不做什么。
14. 长期人力账，包括用户和团队是否被消耗。
15. 下一步 PM 决策，包括继续加深、收缩、验证、停止或延后。

最后用高级 PM 的语言收束：不要只说“建议优化体验”，要说“我会先把目标用户收缩到谁，把哪个工作流做成闭环，用哪三个行为证据验证，如果证据不成立就砍掉哪部分，并明确不做什么”。
