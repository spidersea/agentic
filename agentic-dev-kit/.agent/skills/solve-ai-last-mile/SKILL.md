# 解决 AI 最后一公里

## 核心目标

把用户的模糊意图、外行表达或单句 prompt，转化为一套能让 LLM 稳定发挥能力的复杂问题解决闭环。

默认判断：最后一公里通常不是模型不会，而是用户缺少问题定义、上下文采集、方法选择、结果验收、迭代控制和责任兜底。不要只优化 prompt，要把专家工作方式产品化。

## 使用原则

- 先还原任务，再回答问题。不要把症状当问题。
- 先建立任务合同，再生成内容。不要让模型在缺少成功标准时自由发挥。
- 先判断 AI 是否适用，再设计 AI 流程。非 AI 路径更便宜时要明说。
- 先识别风险等级，再决定回答深度。监管、医疗、法律、金融、安全场景必须保守。
- 先补关键 context，再追求完整 context。不要让追问变成负担。
- 先选择专家协议，再组织输出。不要把所有复杂问题都塞进通用聊天。
- 先审查可执行性，再包装表达。不要把说服力当正确性。
- 先给用户可采用的下一步，再给宏大解释。复杂问题必须落到行动。
- 面向小白时先让用户能动起来，再暴露完整专业框架。术语必须翻译成可填字段和下一步动作。
- 用产品视角复核解题结果。每个复杂输出都要问：它是否打赢旧路径，是否降低迁移成本，是否有责任兜底，是否能复用。

## 快速分流

先判断用户请求属于哪类：

| 类型 | 处理方式 |
|---|---|
| 简单知识或低风险写作 | 直接回答，可顺手改写为更好的 prompt |
| 模糊但可推进的问题 | 说明关键假设，主动补 3-5 个 context 点后给初稿 |
| 高风险或复杂决策 | 先建立任务合同，再进入专家协议和反方审查 |
| 用户想学会使用 AI | 输出可复用操作法、模板和练习闭环 |
| 用户要做成产品/流程 | 输出工作流、验收指标、失败兜底和不做项 |
| 用户要验证、打磨或循环化 AI/Agent 工作流 | 加载 [loop-engineering.md](references/loop-engineering.md)，把一次性答案改成证据驱动的持续闭环 |
| 涉及法规、价格、市场、标准、医疗、金融、政策 | 要求当前权威来源验证；无法验证时标为未核实 |

## 三层融合闭环

本 skill 不是单纯 prompt 优化器。每次复杂任务都按三层推进：

| 层级 | 作用 | 不通过时怎么处理 |
|---|---|---|
| 解题层 | 把小白问题转成任务合同、领域模型、专家协议和任务卡 | 回到小白护栏，减少字段和术语 |
| 产品层 | 判断这套 AI 解法是否比旧路径更便宜、更可靠、更能复用 | 收缩到更小闭环，或推荐非 AI 路径 |
| 验证层 | 用小白/专家双角色和跨场景压力测试检查泛化 | 如果换行业也成立或专家要推倒重来，重做领域模型 |

最终输出必须同时服务两个人：小白用户知道下一步怎么补信息，领域专家能少量修改后继续推进。

## Loop 循环工程入口

当用户要求把 prompt、skill、agent、AI 产品流程或复杂决策方法“优化、产品化、可持续验证、可复用、能闭环”时，读取 [loop-engineering.md](references/loop-engineering.md)，把本 skill 从一次性交付切换为循环工程模式：`任务合同 -> 最小闭环 -> 证据设计 -> 执行/验证 -> 失败升级 -> 规则沉淀 -> 终态判定`。

## 小白护栏

当用户明显不是领域专家时，把专业框架折叠成低负担交互：

- 先给一个“我先替你理解成……”的任务改写，让用户确认或修正。
- 把专业术语翻译成日常问题，例如把“目标交付物”写成“你最后想拿到什么”。
- 对未知信息写“待补”，不要要求用户一次性补全所有字段。
- 每次最多给 3 个必须回答的问题，并说明“不回答也可以先用默认假设推进”。
- 给用户一段可复制的任务卡，让用户下次能直接粘给 AI。
- 对高风险场景要温和但明确：AI 可以帮你准备问题和材料，不能替你做最终专业决定。

小白模式的首屏优先结构：

```markdown
**我先替你把问题翻译成可解任务**
...

**先回答这 3 个问题就够**
1. ...
2. ...
3. ...

**在你没补充前，我先按这些假设推进**
- ...

**可直接复制给 AI 的任务卡**
...
```

## 最后一公里缺口图

诊断用户卡在哪一层，不要默认是 prompt 问题：

| 缺口 | 典型表现 | 该补的能力 |
|---|---|---|
| 问题定义 | 用户说的是症状、愿望或口号 | 把请求改写成决策、任务或交付物 |
| 上下文采集 | 用户不知道该提供什么背景 | 主动追问角色、场景、约束、旧方案、风险 |
| 方法选择 | 用户只说“分析一下” | 选择诊断、对标、拆解、实验、规划或审查协议 |
| 结果验收 | 用户不知道答案好不好 | 给出判断标准、风险、反例和专家审稿点 |
| 迭代控制 | 用户反复抽卡式追问 | 固定迭代循环：假设、输出、审查、修正、沉淀 |
| 责任兜底 | AI 建议直接进入执行 | 标明人工确认、撤回、审计、保守边界和失败恢复 |

## 三道前置闸门

在复杂或跨行业问题中，先过三道闸门，再进入专家协议。

### 1. AI 适用性闸门

判断这个问题是否真的应该用 AI：

| 判断项 | 通过标准 |
|---|---|
| 任务是否需要判断 | 不是简单搜索、规则匹配、模板替换或固定流程 |
| AI 是否有增量 | 能综合模糊信息、生成备选方案、发现风险或加速专家初稿 |
| 非 AI 路径是否更便宜 | 如果表单、规则、搜索、计算器、专家电话更便宜，要优先推荐非 AI |
| 执行风险是否可控 | AI 只生成建议、草案、检查表；高风险执行必须人工确认 |

如果 AI 不适用，输出“更低成本路径”，不要强行包装成 AI 方案。

### 2. 行业对象建模闸门

任何行业问题都先补齐最小领域模型：

```markdown
**领域模型**
- 行业对象：病人/订单/设备/课程/资产/门店/案件/项目/内容/客户等
- 所处环节：获客、诊断、生产、交付、运营、风控、售后、复盘等
- 关键角色：决策者、执行者、受影响者、监管者、买单者
- 价值指标：收入、成本、时效、质量、安全、合规、满意度、留存等
- 数据证据：用户提供、系统记录、外部资料、专家经验、待核实来源
- 时间尺度：一次性决策、日常运营、季度策略、长期能力建设
- 失败模式：误判、延迟、违规、事故、投诉、返工、成本失控
- 约束边界：预算、权限、法规、设备、人力、品牌、伦理、安全
- 交付形态：方案、SOP、清单、模型、文案、代码、实验、报告
```

如果输出放到任何行业都成立，说明领域模型不够，必须重做。

### 3. 风险分级闸门

先给风险等级，再决定能回答到哪一步：

| 等级 | 场景 | 允许输出 | 必须兜底 |
|---|---|---|---|
| L0 低风险 | 创意、学习、低成本写作 | 可直接给完整初稿 | 标明假设和可选方案 |
| L1 业务风险 | 运营、营销、产品、管理、B2B 决策 | 给方案、指标、实验和风险 | 要求用真实数据验证 |
| L2 专业/监管风险 | 法律、财税、金融、医疗健康、合规、政策 | 给问题清单、资料框架、决策备忘录 | 要求权威来源和专业人士确认 |
| L3 安全/生命/重大资产风险 | 临床治疗、公共安全、施工、交通、电网、化工、网络安全实战 | 只给准备清单、沟通框架、风险识别 | 不替代现场专家，不直接给执行指令 |

涉及法律、政策、价格、市场、标准、软件版本、医疗指南等可能变化的信息时，必须使用当前权威来源；如果无法联网或无法验证，明确写“当前性未核实”。

## 标准工作流

### 1. 建立任务合同

把用户请求压缩成一份工作委托：

```markdown
**任务合同**
- 要解决的核心问题：
- 用户真正要做的决策或交付物：
- 使用结果的人：
- 当前旧方案或替代路径：
- 领域对象和所处环节：
- 成功标准：
- 已知 context：
- 数据证据和待核实来源：
- 关键约束：
- 错了的代价：
- 风险等级：
- 需要 AI 承担的部分：
- 必须由人确认的部分：
```

如果用户没有提供足够信息，优先补这些问题：

1. 这个结果最后要用在哪里？
2. 你现在卡住的是事实不足、判断冲突，还是执行路径不清？
3. 有哪些不能违反的约束？
4. 旧方案是什么，为什么不够好？
5. 如果答案错了，谁会承担成本？

### 2. 选择交付物形态

先确定专家最后会交付什么，避免把所有问题都写成泛泛建议：

| 领域类型 | 优先交付物 |
|---|---|
| 运营/供应链/门店/服务 | 流程图、SOP、岗位分工、指标看板、异常处理 |
| 制造/工程/设备/技术 | 架构或工艺假设、约束表、测试计划、回滚方案 |
| 法律/财税/金融/合规 | 决策备忘录、证据清单、风险矩阵、专家确认问题 |
| 医疗/照护/心理/安全 | 沟通准备、观察记录、风险信号、专业求助路径 |
| 教育/培训/组织 | 学习画像、干预方案、练习闭环、评估量表 |
| 内容/品牌/创意 | 创意 brief、受众画像、表达策略、样稿、评审标准 |
| 产品/商业/战略 | 用户假设、旧路径、迁移成本、实验设计、不做项 |

### 3. 选择专家协议

根据任务类型选择一个或组合多个协议：

| 场景 | 推荐协议 | 核心动作 |
|---|---|---|
| 产品/商业判断 | PM 诊断协议 | 旧路径、迁移成本、用户证据、责任流、战略放弃 |
| 技术方案 | 工程审查协议 | 目标、约束、架构、边界、测试、回滚 |
| 研究学习 | 研究协议 | 概念边界、资料来源、争议点、可迁移模型 |
| 写作表达 | 读者协议 | 读者、立场、证据、结构、语气、发布场景 |
| 运营/流程 | 流程协议 | 触发、输入、处理、确认、执行、反馈、恢复 |
| 个人决策 | 决策协议 | 目标、选项、代价、不可逆性、后悔最小化 |
| 创业/战略 | 战略协议 | 用户、场域、差异、资源、节奏、不做项 |

不要把协议当清单罗列。每一步都要解释它为什么影响最终判断。

### 4. 运行四角色推理

对复杂问题至少经过四个角色：

1. **诊断者**：重写问题，识别根因、假设和缺失 context。
2. **方案者**：给出可执行路径、优先级和交付物。
3. **反方审查者**：寻找漏洞、误判、反例、责任风险和低成本替代方案。
4. **验收者**：按成功标准判断是否达到专业初稿，列出还需补证的地方。

输出时不要模拟人格表演，直接给四段判断即可。

### 5. 生成可执行初稿

结果必须包含：

- 对问题的重新定义。
- 明确假设和证据边界。
- 结构化方案或判断。
- 风险、反例和失败条件。
- 用户下一步能做的动作。
- 可复用的 prompt、任务合同或检查表。
- 哪些地方需要专家、人类或真实数据确认。

### 6. 做验收和沉淀

用以下标准判断是否通过：

| 验收项 | 通过标准 |
|---|---|
| 普通用户可用 | 用户不需要自己设计专业 prompt |
| 专业初稿水平 | 专家审阅时不需要推倒重来 |
| 上下文充分 | 关键假设、缺失信息和风险被标明 |
| 可执行 | 有下一步动作，不只是观点 |
| 可迭代 | 用户知道如何补资料、修正和继续推进 |
| 可迁移 | 沉淀出下次处理同类问题的方法 |

默认 80% 验收定义：在一个明确领域或任务族内，普通用户经过任务合同、上下文追问、专家协议、反方审查和验收后，能得到可被专家少量修改后采用的专业初稿。

### 7. 循环工程化

当任务不是一次性交付，而是要变成可复用 AI 工作流、agent 流程、skill 或产品能力时，按 [loop-engineering.md](references/loop-engineering.md) 补齐循环对象、证据账本、失败升级、记忆沉淀和终态判定。

## 真实质量验收门

结构齐全不等于质量通过。每次复杂输出在结束前必须过 6 道真实质量门；任一不通过，就先修正输出，再给用户最终版。

| 质量门 | 必须满足 | 不通过的典型表现 |
|---|---|---|
| 领域关键变量 | 点出该领域真正影响结果的 5-8 个变量 | 换个领域也能用 |
| 小闭环收缩 | 把大目标压成 1-2 个可执行闭环 | 同时要求用户做太多事 |
| 可量化验收 | 给出 1/2/4 周能观察的指标 | 只有“坚持、提升、优化” |
| 执行负担 | 控制用户每天/每周投入，说明最低可行版本 | 计划正确但普通人执行不了 |
| 失败降级 | 写明无效、抵触、风险升高时怎么降级或求助 | 一条路走到底 |
| 专家交接 | 标明应给老师/医生/律师/工程师/负责人看的材料 | 专家还要重新访谈 |

禁止把“有任务卡、有风险等级、有产品诊断”当成通过。必须回答：用户明天具体做什么、怎么知道有效、无效时怎么改、谁能接手。

### 教育/学习类额外质量门

涉及孩子、学习、训练、组织成长时，额外检查：

- 是否区分知识漏洞、方法问题、习惯问题、动机/情绪问题。
- 是否避免三科或多目标同时重压。
- 是否给出亲子关系或心理负担兜底。
- 是否建议家校/教练/老师用真实作业和错题确认。
- 是否有 2 周和 4 周复盘指标，而不是只给长期愿望。

## 产品诊断复核

对复杂任务卡进行一次轻量 AI 产品诊断。不要把生成了结构化内容当成有效，要判断它是否形成新的工作契约。

### 1. PM verdict

给出下面之一：

| verdict | 使用条件 | 下一步 |
|---|---|---|
| 可用 | 用户能低成本补信息，专家可少量修改后采用，风险边界清楚 | 继续输出任务卡和执行路径 |
| 方向对但应收缩 | 任务太大，但有一个小闭环可先跑 | 收缩到一个具体对象、场景和交付物 |
| 暂不适合 AI | 规则、搜索、表单、计算器、专家电话更便宜 | 输出更低成本路径 |
| 高风险只做准备 | 医疗、法律、金融、安全、重大资产等不能由 AI 直接决策 | 输出资料清单、沟通框架和专家确认问题 |
| 证据不足 | 缺少真实数据、用户场景或验收标准 | 标明待补证据，不假装已经成立 |

### 2. 产品五问

每个复杂输出都用这五问复核：

1. **旧路径是什么**：用户原来会直接问 AI、找专家、查资料、套模板还是走组织流程？
2. **AI 增量是什么**：本 skill 省掉了哪一步，是否只是把旧模板说得更漂亮？
3. **迁移成本是什么**：用户多填了哪些字段、多承担了哪些确认和理解成本？
4. **责任流是否清楚**：AI 负责草案、检查、提问还是执行？谁确认、谁撤回、谁兜底？
5. **复用证据是什么**：用户是否能下次复用任务卡，专家是否不需要推倒重来？

### 3. 产品级失败条件

出现任一情况，不能标为有效：

- 输出内容换到任何行业仍然成立。
- 只生成建议，没有任务卡、验收标准或下一步动作。
- 让用户承担更多输入成本，却没有明显提高答案质量。
- 高风险场景没有风险等级、权威来源、人工确认或失败兜底。
- 小白看完不知道该补什么，专家看完必须重新访谈。
- 把合成测试、口头认可、一次试用当成真实迁移证据。

### 4. 真实有效性证据

证据从弱到强排序：

| 证据 | 解读 |
|---|---|
| 小白觉得清楚 | 只说明表达友好，不说明产品成立 |
| 小白愿意补 3 个关键信息 | 说明启动成本可接受 |
| 专家少量修改后采用任务卡 | 说明专业初稿成立 |
| 用户下次主动复用任务卡 | 说明迁移开始发生 |
| 任务卡替代旧 prompt 或旧模板 | 说明旧路径被打赢 |
| 出错后仍继续使用并能修正 | 说明信任和反馈闭环成立 |

## 场景验证协议

当用户要求验证、打磨或产品化这个 skill 时，用“AI 产品诊断 + 小白使用者 + 顶级专家审查者”做压力测试：

1. 让小白提出模糊请求：只说愿望、症状或“帮我分析一下”。
2. 用本 skill 把请求转成任务合同、领域模型、风险等级和交付物。
3. 让专家审查是否缺少领域对象、关键约束、真实数据、失败模式和兜底。
4. 用产品诊断复核旧路径、迁移成本、责任流、证据污染和可复用性。
5. 如果专家认为“换个行业也能用”，判为未通过，回到领域模型重做。
6. 如果小白看不懂或不知道下一步做什么，判为未通过，回到小白护栏重写。
7. 如果高风险任务没有专业确认、当前来源或人工兜底，判为未通过。
8. 如果产品诊断认为旧路径更便宜，判为暂不适合 AI，输出非 AI 路径。

验收至少同时满足：小白能继续补信息，专家不需要推倒重来，风险边界清楚，结果能沉淀成下次可复用任务卡，并通过“真实质量验收门”。

### 100 场景校准

100 场景验证只用于发现系统性缺口和结构覆盖问题，不能当作真实用户迁移证据，也不能单独声明 skill 最终通过。若是为了产品化、skill 打磨或长期工作流验证，按 [loop-engineering.md](references/loop-engineering.md) 记录 evidence ledger、失败升级和终态判定。校准时覆盖这些场景族：

| 场景族 | 专家重点审查 |
|---|---|
| 运营/门店/供应链 | 是否落到对象、流程、指标、异常处理 |
| 制造/工程/设备/技术 | 是否有约束、测试、回滚、安全边界 |
| 法律/财税/金融/合规 | 是否变成证据清单、风险矩阵、专家确认问题 |
| 医疗/照护/心理/公共安全 | 是否只做准备和风险识别，不做最终决策 |
| 教育/培训/组织 | 是否有学习画像、练习闭环、评估方式 |
| 内容/品牌/创意 | 是否有受众、渠道、立场、样稿和评审标准 |
| 产品/商业/战略 | 是否有旧路径、迁移成本、实验和不做项 |

每个场景记录：

```markdown
- 行业/场景：
- 小白原始问题：
- 任务卡是否能让小白继续补信息：
- 专家是否少量修改后可采用：
- 产品诊断 verdict：
- 真实质量门是否通过：
- 证据编号和验证方法：
- 循环动作：keep / revise / discard / escalate
- 失败原因：
- 应写回 skill 的规则：
```

只有当同一失败原因在多个场景复现，才写回 skill；不要为单个特殊案例堆规则。若 100 场景由同一模型生成、作答、评分，结论只能写“覆盖性回归通过”，不能写“真实质量通过”。若没有连续观察证据，不能写“循环工程终态通过”。

### 最终验收证据

最终验收必须至少包含一个真实或用户提供的具体案例，并对最终回答做反向审查：

```markdown
- 真实案例：
- 初稿主要缺陷：
- 修正动作：
- 6 道真实质量门结果：
- 用户明天能做的动作：
- 2 周/4 周验收指标：
- 失败降级和专家交接：
```

## 追问规则

- 最多先问 3 个最关键问题，除非用户明确要求深度访谈。
- 每个问题都要说明会改变哪个判断。
- 不要问用户可以从常识推断或从上下文获取的问题。
- 问完仍要给一个基于当前信息的暂定版本。
- 对高风险医疗、法律、金融、安全等场景，必须强调人类专家确认和风险边界。

## 反模式

避免这些输出：

- 只给“高级 prompt”，不帮用户定义任务。
- 只生成漂亮答案，不标明假设、证据和风险。
- 不问场景，直接扮演专家。
- 把用户夸奖当成验证。
- 把复杂问题做成一次性回答，没有迭代闭环。
- 让 AI 直接承担执行责任，却没有人工确认、撤回或审计。
- 用通用聊天框承接本该结构化处理的任务。

## 质量标尺

好的最后一公里输出，应该让用户获得三样东西：

1. **当前问题的可用结果**：这次真的能推进。
2. **下一步的行动路径**：知道补什么、做什么、找谁确认。
3. **下次复用的方法**：用户不只是得到答案，还学会一类问题的解法。

如果只给答案，没有让用户更会使用 AI，这个 skill 没有完成。
