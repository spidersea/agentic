# 输出模板与场景校准

> 本文档从 SKILL.md 提取，按需加载以减少 Token 消耗。

## 100 场景校准

100 场景验证只用于发现系统性缺口和结构覆盖问题，不能当作真实用户迁移证据，也不能单独声明 skill 最终通过。若是为了产品化、skill 打磨或长期工作流验证，按 [loop-engineering.md](loop-engineering.md) 记录 evidence ledger、失败升级和终态判定。校准时覆盖这些场景族：

| 场景族 | 专家重点审查 |
|---|---|
| 运营/门店/供应链 | 是否落到对象、流程、指标、异常处理 |
| 制造/工程/设备/技术 | 是否有约束、测试、回滚、安全边界 |
| 法律/财税/金融/合规 | 是否变成证据清单、风险矩阵、专家确认问题 |
| 医疗/照护/心理/公共安全 | 是否只做准备和风险识别，不做最终决策 |
| 教育/培训/组织 | 是否有学习画像、练习闭环、评估方式 |
| 内容/品牌/创意 | 是否有受众、渠道、立场、样稿和评审标准 |
| 产品/商业/战略 | 是否有旧路径、迁移成本、实验和不做项 |

每个场景记录：

```markdown
- 行业/场景：
- 小白原始问题：
- 任务卡是否能让小白继续补信息：
- 专家是否少量修改后可采用：
- 产品诊断 verdict：
- 真实质量门是否通过：
- 证据编号和验证方法：
- 循环动作：keep / revise / discard / escalate
- 失败原因：
- 应写回 skill 的规则：
```

只有当同一失败原因在多个场景复现，才写回 skill；不要为单个特殊案例堆规则。若 100 场景由同一模型生成、作答、评分，结论只能写"覆盖性回归通过"，不能写"真实质量通过"。若没有连续观察证据，不能写"循环工程终态通过"。

### 最终验收证据

最终验收必须至少包含一个真实或用户提供的具体案例，并对最终回答做反向审查：

```markdown
- 真实案例：
- 初稿主要缺陷：
- 修正动作：
- 6 道真实质量门结果：
- 用户明天能做的动作：
- 2 周/4 周验收指标：
- 失败降级和专家交接：
```

## 输出模板

重要问题使用这个结构：

```markdown
**最后一公里判断**
[说明用户真正卡在哪一层：问题定义、context、方法、验收、迭代或责任。]

**任务合同**
- 核心问题：
- 目标交付物：
- 使用场景：
- 旧方案：
- 领域对象和所处环节：
- 成功标准：
- 关键约束：
- 风险等级：
- 错误代价：
- 当前假设：

**领域模型**
- 关键角色：
- 价值指标：
- 数据证据：
- 失败模式：
- 交付形态：

**需要补的最小 context**
- ...

**AI 适用性判断**
[说明为什么用 AI，或为什么更低成本路径不是 AI。]

**专家协议选择**
[说明为什么选这个协议，以及不用哪些协议。]

**产品诊断复核**
- PM verdict：
- 旧路径：
- AI 增量：
- 迁移成本：
- 责任流：
- 有效性证据：

**真实质量验收**
- 领域关键变量：
- 小闭环：
- 量化指标：
- 执行负担：
- 失败降级：
- 专家交接：

**解题过程**
1. 诊断者：
2. 方案者：
3. 反方审查者：
4. 验收者：

**可执行结果**
[给出方案、判断、文案、计划、架构或流程。]

**风险和兜底**
- 主要风险：
- 反例：
- 必须人工确认：
- 失败后怎么恢复：

**可复用提示词或任务卡**
[把这次经验沉淀成用户下次可直接复用的 brief。]
```

对于轻量请求，可以压缩为：

```markdown
**我先把问题改写成可解任务：**
...

**建议这样问 AI：**
...

**用这个标准验收：**
...
```
