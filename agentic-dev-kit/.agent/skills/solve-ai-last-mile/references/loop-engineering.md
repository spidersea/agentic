# Loop 循环工程协议

使用本文件处理需要“持续验证、产品化、可复用、可迁移、能闭环”的 AI/Agent 工作流、prompt、skill 或复杂决策方法。普通一次性回答不需要加载本文件。

## 核心原则

- 用证据闭环替代信心闭环：每轮必须留下可复查的输入、输出、验证和结论。
- 用最小循环替代宏大系统：先让一个对象、一个场景、一个交付物稳定跑通。
- 用失败升级替代原地微调：重复失败时切换方法、收缩范围或停止宣称有效。
- 用沉淀门槛替代经验堆料：只有跨场景复现的规则才写回 skill、SOP 或模板。
- 用终态判定替代单次通过：连续观察窗口内 PASS 且无未接受 WARN/CRITICAL，才称为稳定。

## 适用触发

读完 `SKILL.md` 后，如果出现以下请求，启用本协议：

- 优化、打磨、产品化一个 prompt、skill、agent、工作流或 AI 方法。
- 要求验证“是否真的有效”“能不能泛化”“能不能复用”。
- 用户已经有一次性答案，但想变成长期使用的流程、模板、SOP 或训练系统。
- 输出会影响多个用户、团队流程、业务决策或高风险专业准备。

## 最小循环定义

先把目标压缩成一个可运行循环：

```markdown
**最小循环**
- 循环对象：要反复处理的具体对象是什么？
- 触发条件：什么输入会启动这轮？
- 输入包：用户/系统/专家必须提供哪些最小 context？
- 处理协议：AI 具体负责诊断、生成、审查、验证还是沉淀？
- 输出物：每轮产生什么可检查结果？
- 验证方法：用什么证据判断 keep / revise / discard？
- 失败恢复：失败后降级、转人工、换方法还是停止？
- 记忆写回：什么条件下把经验写回 skill、模板或 SOP？
```

如果循环对象写不清，先回到任务合同和领域模型，不要直接设计流程。

## Evidence Ledger

每轮都记录证据，哪怕只是轻量文本账本：

```markdown
- evidence_id:
- timestamp:
- scenario:
- input_snapshot:
- output_artifact:
- verification_method:
- verdict: PASS / WARN / FAIL / CRITICAL
- failure_class:
- decision: keep / revise / discard / escalate
- rule_candidate:
- human_or_expert_confirmation:
```

证据强度从弱到强排序：

| 证据 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 自评通过 | 结构可能完整 | 不能证明真实有效 |
| 合成场景通过 | 覆盖面可能变广 | 不能证明用户迁移 |
| 用户能补最小 context | 启动成本可接受 | 不能证明专业质量 |
| 专家少量修改后采用 | 专业初稿成立 | 不能证明长期复用 |
| 用户下次主动复用 | 迁移开始发生 | 不能证明稳定终态 |
| 连续多轮真实 PASS | 稳定性增强 | 仍需监控 WARN/CRITICAL |

## 失败升级

同类失败不要连续微调措辞。按失败次数升级：

| 连续失败 | 动作 | 输出要求 |
|---|---|---|
| 1 次 | 修正明显缺口 | 写明修正了哪个证据缺口 |
| 2 次 | 切换方法 | 从 prompt 改为任务合同、从通用协议改为领域协议，或从生成改为验证 |
| 3 次 | 收缩闭环 | 缩到单一对象、单一角色、单一交付物 |
| 4 次 | 反方审查 | 明确最可能失败的场景和旧路径更便宜的可能 |
| 5+ 次 | 停止宣称有效 | 输出失败报告、保留证据、请求真实样本或专家输入 |

失败分类至少包括：

- `context_gap`：缺少关键场景、角色、约束或数据。
- `domain_generic`：输出换行业也成立。
- `validation_gap`：没有可观察指标或验收证据。
- `execution_burden`：用户执行成本过高。
- `risk_boundary`：高风险边界、权威来源或人工确认不足。
- `product_mismatch`：AI 路径没有打赢旧路径。
- `memory_bloat`：把单例经验写成通用规则。

## 记忆和规则写回

只有满足以下条件之一，才建议写回 skill、模板或 SOP：

- 同一失败分类在 3 个以上不同场景复现。
- 专家确认某条规则是领域硬约束。
- 用户已经连续复用任务卡，并暴露相同摩擦。
- 高风险边界遗漏可能造成严重误导，必须立即补护栏。

写回时要删除或替换旧规则，避免只追加。每条新规则都要能回答：

- 它修复了哪个复现失败？
- 它适用于哪些场景，不适用于哪些场景？
- 它会增加多少用户输入成本？
- 它是否让小白更难启动？

## 终态判定

不要用“看起来更完整”宣称终态。终态至少需要：

- 一个真实或用户提供案例通过。
- 一个跨场景回归集通过。
- 最近观察窗口无未接受 WARN/CRITICAL。
- 失败样本被分类，重复失败有处理动作。
- 规则写回有证据编号，不是主观偏好。

可使用项目中的 loop 工具时，对齐这些命令语义：

- `loop-health.sh --record`：记录循环工程健康证据。
- `loop-terminal-verdict.sh 7`：只有连续 7 个不同 PASS 日且无近期 WARN/CRITICAL 才允许称为终态。
- `safe-rollback.sh status`：破坏性回滚前检查是否允许。

无法运行工具时，在回答中给出等价的文本证据账本和 pending 条件。
